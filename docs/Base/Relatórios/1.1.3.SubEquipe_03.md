# SubEquipe_03 — Strategy na seleção de anúncios



A SubEquipe_03 aplica o padrão **Strategy** à seleção de anúncios do fórum. Esta seção relaciona o problema de negócio, as duas visões UML e os trechos que evidenciam o padrão no código. A implementação completa fica no repositório e na [página complementar de código](/Base/Codigos/1.1.3.Codigo_SubEquipe_03.md).



### Contexto do problema e fundamentação

Ao abrir uma pergunta, o fórum precisa escolher um anúncio compatível com suas tags, considerando a situação e o saldo das campanhas. A regra de prioridade pode variar: escolher um candidato de maneira determinística ou priorizar a campanha com maior saldo. Quando não há candidato elegível, deve ser exibido um anúncio genérico. Misturar essas decisões nas rotas dificultaria acrescentar políticas e testar cada algoritmo isoladamente.

Segundo Gamma et al. (2000), Strategy encapsula algoritmos de uma mesma família em objetos intercambiáveis, permitindo variar o comportamento usado pelo cliente. No projeto, `ControladorEntrega` é o **Context**, `EstrategiaSelecaoAnuncio` define o contrato **Strategy** e as três classes de seleção são **ConcreteStrategy**. O controlador delega a seleção pelo contrato comum; o registro resolve a política configurada, e o controlador aciona o fallback quando o resultado principal é `None`.

Em Python, o contrato usa `typing.Protocol`: a compatibilidade é estrutural, sem exigir herança explícita das estratégias. A checagem com `@runtime_checkable` verifica a presença dos membros, mas não prova a compatibilidade completa de suas assinaturas; por isso os testes continuam necessários ([Python Typing](https://typing.python.org/en/latest/reference/protocols.html)).

O diagrama organiza a seleção de anúncios em torno do padrão **Strategy**, separando a coordenação do fluxo das regras que escolhem o anúncio. O `ControladorEntrega` representa o **Context**, responsável por solicitar a seleção, enquanto `EstrategiaSelecaoAnuncio` representa o contrato **Strategy**, comum aos algoritmos disponíveis. As estratégias concretas encapsulam as diferentes políticas, e os elementos do domínio, como pergunta, tags, campanhas e anúncios, fornecem os dados necessários à decisão.

As **ConcreteStrategy** representam três comportamentos: a seleção por correspondência de tags com desempate determinístico, a priorização da campanha elegível com maior saldo e o fornecimento de um anúncio genérico. As duas primeiras trabalham com candidatos contextuais; a terceira funciona como alternativa quando a política principal não encontra um anúncio elegível. A decisão de acionar essa alternativa pertence ao controlador, não às estratégias contextuais.

O ponto central do **Strategy** é que o controlador depende do contrato comum, e não dos detalhes de cada algoritmo. Assim, ele delega a seleção à estratégia configurada sem precisar distinguir qual política está em uso. Essa estrutura permite substituir o comportamento de seleção e acrescentar novas políticas por meio de implementações e de seu registro, preservando a lógica de coordenação. Também facilita testar cada algoritmo isoladamente, mantendo as regras de seleção separadas da apresentação, da cobrança e do registro de métricas.

#### 1. Strategy: contrato comum

```python
    def selecionar_anuncio(
        self, pergunta: Pergunta, campanhas: list[Campanha]
    ) -> Anuncio | None:
        ...

    def obter_nome(self) -> str:
        ...
```

Fonte: [model/strategies.py](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G2_ProjetoForum_Entrega03/blob/81b1f13beb46a99830dd9a5f02df5fb2286c50f5/codigo/subequipe3_strategy/ads/model/strategies.py).

O retorno opcional permite comunicar ausência de candidato sem executar fallback dentro de uma estratégia contextual. `obter_nome()` identifica a política. As três implementações atendem a esse contrato.

#### 2. Context: delegação e fallback

```python
anuncio = estrategia.selecionar_anuncio(pergunta, campanhas)
if anuncio is None:
    estrategia = self._fallback
    anuncio = estrategia.selecionar_anuncio(pergunta, campanhas)
    if anuncio is None:
        raise FallbackSemAnuncio(
            f"A estratégia de fallback '{estrategia.obter_nome()}' não devolveu anúncio."
        )
```

Fonte: [controller/controlador_entrega.py](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G2_ProjetoForum_Entrega03/blob/81b1f13beb46a99830dd9a5f02df5fb2286c50f5/codigo/subequipe3_strategy/ads/controller/controlador_entrega.py).

Este recorte pertence a `entregar_anuncio()`, depois da consulta da pergunta e das campanhas. O Context não distingue `match_exato` de `maior_saldo`; somente trata ausência de anúncio. A guarda final detecta uma configuração de fallback que descumpra seu contrato. O método devolve `EntregaAnuncio`, incluindo pergunta, anúncio, política usada e indicação de fallback.

#### 3. ConcreteStrategy: o que muda entre os algoritmos

As duas estratégias contextuais primeiro filtram campanhas ativas, com tags em comum e saldo suficiente para um CPC positivo. A comparação de nomes de tags ignora diferenças entre maiúsculas e minúsculas. Os trechos abaixo mostram apenas a decisão final, sobre os candidatos já filtrados.

**Match exato:** a tupla contém `(id_campanha, id_anuncio, anuncio)`; vence o menor par de IDs.

```python
vencedor = min(candidatos, key=lambda item: item[:2], default=None)
return vencedor[2] if vencedor is not None else None
```

Fonte: [model/match_exato.py](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G2_ProjetoForum_Entrega03/blob/81b1f13beb46a99830dd9a5f02df5fb2286c50f5/codigo/subequipe3_strategy/ads/model/match_exato.py).

**Maior saldo:** a tupla contém `(saldo, id_campanha, id_anuncio, anuncio)`; vence o maior saldo, com desempate pelos menores IDs.

```python
vencedor = max(
    candidatos,
    key=lambda item: (item[0], -item[1], -item[2]),
    default=None,
)
return vencedor[3] if vencedor is not None else None
```

Fonte: [model/maior_saldo_strategy.py](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G2_ProjetoForum_Entrega03/blob/81b1f13beb46a99830dd9a5f02df5fb2286c50f5/codigo/subequipe3_strategy/ads/model/maior_saldo_strategy.py).

**Genérico:** o método `selecionar_anuncio()` devolve a instância recebida no construtor, com ID estável e sem campanha paga.

```python
return self._anuncio_padrao
```

Fonte: [model/generico.py](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G2_ProjetoForum_Entrega03/blob/81b1f13beb46a99830dd9a5f02df5fb2286c50f5/codigo/subequipe3_strategy/ads/model/generico.py).

Selecionar não altera visualizações, cliques ou saldo. Essas alterações pertencem ao fluxo de entrega e ao repositório de métricas.

#### Fluxo HTTP, métricas e integração

`GET /perguntas/{pergunta_id}/pagina` consulta o Context, monta a página e registra uma visualização após a renderização bem-sucedida. `POST /anuncios/{anuncio_id}/cliques` registra o clique; para anúncios contextuais, revalida a campanha e debita o CPC na mesma operação em memória. Para o genérico, somente incrementa a métrica. O custo não é recebido do navegador. As rotas aparecem em `/docs`.

O [ponto de entrada](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G2_ProjetoForum_Entrega03/blob/81b1f13beb46a99830dd9a5f02df5fb2286c50f5/codigo/subequipe3_strategy/main.py) reutiliza o `app` da SubEquipe_01 e acrescenta as rotas de Ads. Isso preserva a API de Conteúdo, mas não significa que suas perguntas já alimentem Ads: a demonstração usa um seed explícito, e a projeção `projetar_pergunta` preserva o UUID e exige as tags que Conteúdo ainda precisa fornecer.

### Análise crítica e trade-offs

#### Fundamentação das decisões

A relação abaixo explicita a base técnica das decisões e sua aplicação neste projeto. Ela complementa as atas e o código, sem atribuir à literatura regras comerciais específicas do fórum.

| Decisão ou artefato | Fundamentação e aplicação | Limite da escolha |
| --- | --- | --- |
| Encapsular a seleção em estratégias intercambiáveis | Gamma et al. (2000), padrão Strategy: contrato comum e delegação pelo Context. No projeto, os algoritmos recebem pergunta e campanhas sem depender de HTTP | Strategy não define o ranking comercial. Tags, maior saldo e desempate por UUID são escolhas do grupo registradas no épico #23 |
| Usar `Protocol` como contrato | [Python Typing — protocolos](https://typing.python.org/en/latest/reference/protocols.html): implementações podem atender ao contrato estrutural sem herança explícita | A verificação em runtime não substitui tipagem estática nem testes de comportamento |
| Separar composição de dependências e execução | [Fowler (2004)](https://martinfowler.com/articles/injection.html) discute separar configuração de uso; [FastAPI — dependências](https://fastapi.tiangolo.com/tutorial/dependencies/) fornece o mecanismo empregado. Providers e seletor configuram os objetos; o Context utiliza a estratégia recebida | O registro de uma nova política ainda exige alteração no ponto de composição. A escolha de acionar fallback no Context é uma decisão local de coordenação |
| Separar seleção e apresentação HTML | [Starlette — templates](https://www.starlette.io/templates/) documenta `Jinja2Templates` e `TemplateResponse`. A view recebe a entrega e monta a página, enquanto as estratégias apenas selecionam anúncios | A renderização com Jinja2 não comprova a integração das perguntas reais de Conteúdo; o fluxo demonstrado usa o seed |
| Proteger débito e contador no repositório | [Python 3.12 — RLock](https://docs.python.org/3.12/library/threading.html#rlock-objects) fundamenta a exclusão mútua entre threads. O código mantém a atualização conjunta sob a trava e restaura os valores em caso de exceção | A trava não fornece persistência nem uma transação entre processos. A seleção anterior ao clique não reserva saldo |
| Representar o padrão em duas visões UML | [OMG — UML 2.5.1](https://www.omg.org/spec/UML/2.5.1) fundamenta os elementos de notação; Gamma et al. (2000) fundamentam os papéis do Strategy | A divisão teórica/técnica é uma opção de comunicação do grupo. As figuras preservam diferenças em relação ao código, documentadas neste relatório |

O uso de memória foi uma redução de escopo para demonstrar o padrão, não uma recomendação de persistência para produção. Da mesma forma, priorizar maior saldo não demonstra maior receita, relevância ou justiça na distribuição de anúncios: esses objetivos exigiriam requisitos e avaliação próprios. O fallback assegura uma alternativa de exibição, mas a decisão de quando acioná-lo pertence ao fluxo definido pelo grupo.

#### Benefícios e custos observados

| Aspecto | Benefício | Custo ou limite |
| --- | --- | --- |
| Extensão de políticas (OCP) | Nova regra é implementada e registrada sem alterar o Context | O ponto de composição precisa de registro; novas classes aumentam a navegação no projeto |
| Testabilidade | Algoritmos recebem pergunta e campanhas sem HTTP ou banco; providers permitem substituição de dependências | Testes com dublês devem ser complementados por integração com as estratégias reais |
| Separação de responsabilidades | Seleção não cobra nem registra métricas; fallback fica no Context | O fluxo atravessa mais componentes e exige documentação dos contratos |
| Adaptador em memória | Facilita execução, testes e demonstração do padrão | Dados se perdem no reinício; a trava protege somente threads do mesmo processo, sem transação distribuída ou garantia entre workers |

A seleção observa um estado que pode mudar até o clique; por isso o débito revalida elegibilidade e pode responder 409. Cada chamada conta como novo evento, sem deduplicação. As imagens do seed são servidas pela aplicação; os destinos de anúncios são ilustrativos. Faturamento mensal, integrações externas e persistência não foram implementados neste recorte. O limite de cinco tags discutido na Ata 02 é uma proposta para Conteúdo, não uma validação já aplicada pela projeção de Ads.

### Execução e demonstração do padrão Strategy

A demonstração utiliza a aplicação FastAPI integrada ao fórum. O fluxo começa na rota da página da pergunta, passa pelo `ControladorEntrega`, executa a estratégia configurada e entrega o anúncio à view. A view utiliza Jinja2 para preencher o template HTML. Dessa forma, a troca de política pode ser observada na mesma pergunta, sem alterar a rota nem o controlador.

| Política | Trecho responsável pela escolha | Resultado no estado inicial |
| --- | --- | --- |
| `match_exato` | `EstrategiaMatchExatoDeTag` verifica campanha ativa, orçamento e pelo menos uma tag em comum; entre os candidatos, usa os menores UUIDs de campanha e anúncio | Curso de Python |
| `maior_saldo` | `EstrategiaMaiorSaldoNaTag` aplica os mesmos filtros e prioriza o maior saldo; empates usam os menores UUIDs | Comunidade Python |

Para comparar, interrompa o servidor com `Ctrl+C` e, no mesmo terminal e diretório `codigo/`, reinicie com a outra política:

```bash
ADS_POLITICA=maior_saldo python -m uvicorn subequipe3_strategy.main:app
```

Recarregue a mesma página. O anúncio passa a ser Comunidade Python: mudou o algoritmo utilizado pelo controlador, enquanto a pergunta, a rota e a view permanecem iguais. O reinício recria os dados em memória, permitindo comparar as políticas a partir do mesmo estado inicial. A configuração é feita por `ADS_POLITICA`; não existe endpoint gerencial para trocar a política.

#### Observar o fallback

Abra a [pergunta sem campanha compatível](http://127.0.0.1:8000/perguntas/00000000-0000-0000-0000-000000000066/pagina). Sua tag é `desconhecida`, sem correspondência nas campanhas do seed. A estratégia principal devolve `None`; o `ControladorEntrega` aciona `EstrategiaAnuncioGenerico`, e a página mostra Fórum da comunidade. O fallback é decidido pelo controlador, sem uma estratégia chamar outra.

#### Registrar cliques pela API

No [Swagger](http://127.0.0.1:8000/docs), abra **Anúncios → POST /anuncios/{anuncio_id}/cliques**, clique em **Try it out**, informe o identificador e pressione **Execute**. A resposta **204** confirma que o clique foi registrado, sem corpo de resposta.

| Anúncio | Valor de `anuncio_id` | Efeito de uma chamada no seed inicial |
| --- | --- | --- |
| Comunidade Python | `00000000-0000-0000-0000-00000000000c` | Contador de cliques de 0 para 1; débito de R$ 2,00, reduzindo o saldo da campanha de R$ 20,00 para R$ 18,00 |
| Fórum da comunidade | `00000000-0000-0000-0000-00000000001e` | Contador de cliques de 0 para 1; sem débito, pois o anúncio genérico não pertence a uma campanha paga |

A rota chama o controlador, que encaminha a operação ao repositório. O repositório revalida a campanha e, sob a mesma trava, debita o custo por clique e incrementa o contador. No genérico, a campanha é `None`: o débito é ignorado e o contador é incrementado. Cada nova chamada representa outro clique; não há deduplicação.

O HTTP 204 confirma o processamento, mas não apresenta saldo nem contador. O painel auxiliar utilizado na gravação inspeciona esses valores no mesmo processo do servidor para mostrar o antes e o depois; ele não é uma funcionalidade do fórum nem um endpoint de consulta de métricas. Apenas selecionar um anúncio não cobra nem altera métricas; exibir a página registra uma visualização, e o POST registra o clique.

As perguntas e campanhas desse fluxo são dados de demonstração do `RepositorioAds.seed()`, não perguntas criadas automaticamente pelas rotas de Conteúdo. Os dados se perdem ao reiniciar o servidor. A [página complementar de código](/Base/Codigos/1.1.3.Codigo_SubEquipe_03.md) reúne os arquivos completos e as referências dos testes.

#### Testes automatizados

Os testes verificam o comportamento da implementação de forma automatizada. Eles são uma evidência complementar à execução da aplicação e ao vídeo, e não iniciam um servidor para navegação manual.

A suíte cobre contratos, elegibilidade, desempates, ausência de efeitos na seleção, fallback, rotas SSR, métricas e débito. Na revisão do [PR #45](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G2_ProjetoForum_Entrega03/pull/45), a substituição do repositório revelou um provider que ignorava `Depends`; a correção foi acompanhada por teste HTTP com anúncio fora do seed.
