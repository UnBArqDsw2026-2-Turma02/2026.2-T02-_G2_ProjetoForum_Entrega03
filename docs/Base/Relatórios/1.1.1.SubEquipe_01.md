## Foco do Relatório:
### FOCO_01: GoFs Criacionais & IA Generativa
Entrega Mínima: um GoF Criacional (modelo & código & vídeo com o padrão em execução).

**Escolha do Padrão Criacional:**
Para este projeto, optamos por focar no **Factory Method**, aplicado ao subdomínio de criação de `Conteudo` (que engloba Perguntas, Respostas e Comentários). 

**Por que o Factory Method em vez do Builder?**
Durante nossas pesquisas, avaliamos o padrão Builder, porém a criação dos conteúdos no nosso fórum é direta e não envolve a construção de objetos complexos em múltiplas etapas de forma independente. O Factory Method se provou muito mais adequado, pois nos permite instanciar as variações de `Conteudo` delegando a responsabilidade para subclasses específicas. Com isso, conseguimos eliminar a necessidade de lógicas condicionais (como `if/else` para descobrir o tipo do conteúdo) diretamente nos *Controllers* da API, promovendo um baixo acoplamento.

### GoF Criacional
#### Contexto (Problema)

##### Factory Method
No Diagrama de Comunicação "Publicar Pergunta" da Entrega 02, o `PerguntaController` instancia a `Pergunta` diretamente (passo `2.2 criar()`). Desse jeito, cada novo tipo de conteúdo (por exemplo, `Comentario`) obriga a alterar o controller, que passa a conhecer todas as classes concretas. Com o Factory Method, o controller pede o objeto a um **criador** tipado pela abstração `CriadorDeConteudo` e deixa de saber qual classe concreta é instanciada.

##### Singleton (ir além)
Com o Factory Method, cada criador recebe um repositório (`CriadorDePergunta(repositorio)`). O FastAPI, porém, resolve as dependências **a cada requisição**. Se cada requisição recebesse um repositório novo, a pergunta salva no `POST /perguntas` não seria encontrada no `POST /perguntas/{id}/respostas`, e a resposta não apareceria no `GET /perguntas/{id}`. O Singleton (GAMMA et al., 2000) resolve isso: garante que o `RepositorioConteudo` tenha **uma única instância** e oferece um ponto de acesso a ela, de modo que toda a cadeia Pergunta → Resposta → Comentário use a mesma fonte de dados.

**v6 → v7** (revisão da issue #19):
- **Double-checked locking:** `RepositorioConteudo` ganhou o atributo estático `-_lock`, e a nota de `instancia()` mostra o *double-checked locking*.
- **Acesso ao Singleton:** `dependencias` passou a ser o `«Client»` do Singleton e é o único ponto que chama `instancia()`. Os serviços, que antes chamavam `instancia()` direto, passaram a receber o repositório injetado. Assim a dependência fica explícita, o que atenua uma crítica clássica ao Singleton (dependência escondida).
- **Notas do GoF:** foram acrescentadas em `publicar()` (*AnOperation*), nos criadores concretos (`return Produto(...)`) e em `instancia()` (*return uniqueInstance*).
- **Extensões marcadas como `[nao-GoF]`:** o lock com a segunda checagem e a injeção de dependência. A legenda separa os participantes do GoF, o `«Client»` (convenção, já que o GoF não lista Client no Factory Method) e as classes de votação e moderação, que não fazem parte dos padrões criacionais.
- **Construtor:** o GoF usa construtor protegido (`#`) para permitir subclasses. Aqui ele é privado (`-`), porque `RepositorioConteudo` não tem subclasses.

##### Factory Method na API de Perguntas (issue #7)

A F2 partiu da base do PR #32 (Maria Laura), que já trazia os endpoints com `Depends()`. Minha contribuição foi completar os critérios da issue: `tags` na `Pergunta` e os testes de `POST /perguntas` e `GET /perguntas/{id}`.

**Client** (`main.py`): o endpoint recebe o criador pronto, tipado pela abstração, e só chama `publicar()`. Ele não sabe qual classe concreta é instanciada:

```python
@app.post("/perguntas", status_code=201, response_model=PerguntaOut, tags=["Perguntas"])
def criar_pergunta(
    dados: PerguntaIn,
    criador: Annotated[CriadorDeConteudo, Depends(get_criador_de_pergunta)],
):
    return criador.publicar(dados.model_dump())
```

**ConcreteCreator** (`criadores.py`): cada criador sabe criar só o seu produto, sem `if` de tipo:

```python
class CriadorDePergunta(CriadorDeConteudo):
    def criar_conteudo(self, dados: dict) -> Conteudo:
        return Pergunta(corpo=dados["corpo"], titulo=dados["titulo"], tags=dados.get("tags"))
```

Testes em `tests/test_perguntas.py`: 201 com o id, tags opcionais, 422 sem título ou com corpo vazio, GET com tags e respostas, e 404 para id inexistente.

##### Singleton no RepositorioConteudo (issue #19)

**Singleton** (`repositorio.py`): `instancia()` é a operação de classe do GoF. O lock e a segunda checagem são a extensão para concorrência (*double-checked locking*), porque o FastAPI executa endpoints `def` em um pool de threads:

```python
@classmethod
def instancia(cls) -> "RepositorioConteudo":
    if cls._instancia is None:
        with cls._lock:
            # 2ª checagem: outra thread pode ter criado a instância enquanto esta esperava o lock
            if cls._instancia is None:
                cls._instancia = cls(cls._token)
    return cls._instancia
```

**Construtor privado simulado:** Python não tem construtor privado. Só `instancia()` conhece um token privado, e `RepositorioConteudo()` chamado direto lança `TypeError`.

**Client do Singleton** (`dependencias.py`): `get_repositorio()` é o único ponto da API que chama `instancia()`. Criadores e endpoints recebem o repositório via `Depends(get_repositorio)`, então a dependência fica declarada na assinatura:

```python
def get_repositorio() -> RepositorioConteudo:
    # Client do Singleton: único ponto da API que chama instancia()
    return RepositorioConteudo.instancia()
```

**Polimorfismo no lugar de `isinstance`:** com um repositório único para todos os tipos, `GET /perguntas/{id}` com o id de uma resposta encontraria uma `Resposta`. Em vez de testar o tipo, `Conteudo.como_pergunta()` devolve `None` e `Pergunta` sobrescreve o método devolvendo a si mesma. O endpoint responde 404 sem nenhum `if` de tipo.

**Testes** (`tests/test_singleton.py`): mesma instância, construtor bloqueado, `_resetar()`, `salvar`, `buscar_por_id`, `atualizar`, criadores compartilhando a instância e integração ponta a ponta sem substituir o repositório. O teste de concorrência dispara 50 threads ao mesmo tempo. Para garantir que ele realmente detecta a falha, rodamos 20 vezes com três implementações:

| Implementação de `instancia()` | Teste passou |
|---|---|
| Sem lock | 0/20 |
| Com lock, sem a 2ª checagem | 0/20 |
| *Double-checked locking* completo | 20/20 |

A segunda linha mostra na prática por que a segunda checagem é necessária: sem ela, as threads que esperavam o lock criam cada uma a sua instância.

**Senso crítico sobre o Singleton:**
- **Críticas conhecidas:** estado global, dependência escondida, dificuldade de testar e mistura de responsabilidades (ciclo de vida e regra de negócio).
- **Como atenuamos:** o acesso é só por `Depends(get_repositorio)`, e `_resetar()` isola os testes.
- **Limite do padrão:** com `uvicorn --workers 4`, cada **processo** tem o seu Singleton. O padrão garante uma instância por processo, não por sistema. Com banco de dados real, o papel do Singleton passaria a ser o pool de conexões, não os dados.
